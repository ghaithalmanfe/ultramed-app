# UltraMed Field Ops — working notes for Claude

Kuwait dental-products field-sales PWA (two reps + a supervisor). Everything the
team sees must be true: never report "saved" when it did not land, never show a
figure that cannot be explained on screen.

## Layout
- `www/index.html` — markup and CSS only. The app script is split by area into `www/js/app/01-config.js` … `14-ui-boot.js`, loaded in that order as classic scripts sharing ONE global scope (a function in file 07 may call one in file 12 at run time; only code that runs at load must not reference a later file). Add new code to the file whose area it belongs to (a new file needs its two-line header and a `<script src>` tag in the block, in number order). `APP_REV` (top of `01-config.js`) must match `CACHE` in `www/sw.js`; bump both on every release.
- `scripts/build.js` builds what GitHub Pages publishes (`dist/`, git-ignored): the js/app files are inlined back into ONE `<script>` in index.html, so phones get a single self-contained page exactly as before the split. Never list `js/app` files in the service worker's `SHELL` (the build refuses).
- `www/js/core.js` — pure, unit-tested helpers (dates, ERP parsing, merges, month achievement, the daily e-mail digest). Browser-free; `require`-able from Node.
- `www/js/i18n.js` — the English → Arabic dictionary (exact-string matches).
- Weekly management deck (More → "Weekly management deck", supervisor; v111): `UMCore.weeklyReport` computes the week, `UMCore.weeklyStory` keeps only true achievements and `UMCore.weeklyPages` writes every page's text and figures (all pure, unit-tested); `15-weekly-deck.js` only lays them out with PptxGenJS, loaded on demand from `www/js/vendor/pptxgen.bundle.js` (MIT, vendored — no CDN). Harness: `tests/e2e/weekly-deck.e2e.js`. Order (directors' panel): the week's money on one page (four fixed tiles: the week against last week and the earlier weeks' average, the month against target, new business, the average discount), the closed month on days 1–10, the month's plan (counted to the ERP cut-off: what is left, per working day, the same days of last month, named levers), new business, what sold, price discipline, doctors and clinics, the people (the same rows for everyone), next week, our commitments with "Our ask" (only on the close), then the full appendix (A0 contents … A13 method). Truth rules: an invoice above its discount limit is never a hero, a signature or a cover item; the presenter's own sale never leads the cover; the 8-week page runs only when sales lead; samples are not discount; no score where nothing was measured; brands are net of returns, products as invoiced. Language: English, Arabic or both (two files); the speaker notes are Arabic in both. Arabic uses the team's terms, never a literal translation (مبيعات مفوترة، منتجات تدخل العيادات لأول مرة، حسابات رئيسية، المحقق منذ بداية الشهر …), the team's names in Arabic (مريم، رانوفا، د. غيث), pages, tables and charts mirrored right to left. `wdArBidi` adds the bidi marks LibreOffice and PowerPoint need: RLM after "،" only (never a mark between a letter and "،" or "؛" — it garbles the word), LRM before percentages and digit-led Latin names, a negative written as a word or an operator, an amount kept with its currency by a no-break space; a hyperlink run carries one script only. Design (v110): the Smart Vending look — Calibri, dark green 0B2A1B, Ultramed green 1E7A55, yellow F2B705, light cards EEF4F0; `wdIcon` = the app's own line icons. Company-internal ERP accounts ("Marketing …", "… Advertisement": `UMCore.isInternalAccount`) are never wins, and their zero-value moves are not listed as invoices.
- KPI scorecard (More → "KPI scorecard"; v104): `UMCore.kpiScorecard` scores each person on 10 weighted measures (`KPI_ITEMS`; limits in `BENCHMARKS.kpi`, defaults `KPI_DEFAULTS`, edited in "KPI settings" by the supervisor — `saveBenchmarks` must keep `kpi`). Requests, escalations and stands (More → "Requests, escalations & stands", `16-kpi.js`) are stored in `events` with `kind` and `at` and NO `date`, so the calendar and reports ignore them. Government accounts: `UMCore.isGovClinic` (name pattern, overridden by the Gov chip in Admin → Territory). Plan entries carry `at` (time the clinic was planned) so "plan sent before leaving" can be scored. Harness: `tests/e2e/kpi.e2e.js`.

"Bring back the ticked clinics" adds only those (delete log cleared first, recycle-bin copies dropped) and says whether the save landed; visits, tasks and sales files are never touched. The whole-day Restore beside it replaces this month's visits and the tasks — not for a missing clinic; since v121 it refuses a backup of another month (it would have erased this month's visits), says before anything changes how many clinics, tasks and visits it removes, and keeps the sales files (an older index only replaces one with no file at all). v123: it leaves the product catalog as it is, and removes only what is kept somewhere, checked against the cloud as it is now (round 3, re-review 2 and 7; `restoreSnapshotNow`): with no backup yet today, the data as read now is kept first as today's backup (`keptBeforeRestore`; created only if there is still none; measured like the daily backup by `UMCore.snapshotPayload`: above 900 KB without the photo previews; too large or not written → nothing changes). Once today has its backup — the daily one, the copy an earlier restore kept, or today's own backup being restored — a restore NEVER writes it: each document it replaces (clinics, tasks, this month's visits) must be, exactly as the cloud holds it now, in the full backup saved to this device (`_fullBackupSaved.docHash`: the sha256 of each of them as the file holds it; `restoreCover`; only a file handed to the browser counts — round 4: a later read whose sheet was closed without Download had counted as the file on the device, `fullBackupOnDevice`); changed since the file was made → it says which list, asks for a new file and changes nothing (until round 3 any file downloaded within the hour counted, and a second restore wrote over the copy the first had kept). The question says what is removed and where everything it replaces is kept; the lists are read again after the question and written by compare-and-set over exactly that (`persistVisits({ authoritative, expect })` for the visits): a change on another phone in between stops the restore, what it had written is put back and verified document by document, the delete log's revivals are undone (`tombsOf` / `retombMany`), the lists are read again, and the words say whether everything was put back. A write with no answer in time is UNKNOWN, never "unchanged" (round 4: its commit landed after "Nothing was changed" and removed what the restore was stopped for): once the restore stops, a run of its writes writes nothing (`cancelled`, also `persistVisits({ cancelled })`), the document is written as it was all the same (a commit on its way then finds it changed and runs again), and a write that lands late anyway is followed (`storageUpdate(key, fn, ms, onRaw)`) and put back when it does (`restoreFollowLate`); the words say it may still land, and "Nothing was changed" only once that is known (`safety-review.e2e.js` R22, R22b). Still a replace, not an add: what it removes is neither binned nor in the delete log. "Restore from this phone's copy" (the device rows there) compares the copy with the list clinic by clinic (`UMCore.deviceCopyDiff`: not in the list now — deleted ones marked —, fields that differ, doctors only the copy has) and applies only the ticked rows (`applyDeviceCopy`); until v123 it put the old copy back whole. v117/v118 brought clinics back on their own at app start; removed in v119: it downloaded every backup in full on every phone each day (the cloud has no light listing — `storage.list` downloads whole documents) and the cloud showed nothing to bring back. A revival is written down as later than the delete it revives whatever the phone's clock says (`reviveTime`), a phone holding a delete younger than a minute lets it go when the log writes down such a revival, and a delete made after a revival on the same phone is published again (`tomb` clears `_untombed`). The delete log keeps entries 120 days (`TOMB_KEEP_MS`; doctors for good) and carries `rev` (the writer's app revision), `revived` {key: {id: time}} (every revival is written down — a single one by `untomb` also when this phone knew no delete of the record) and `again` (below). An older app (v122) still rewrites the log with its 7-day cutoff, so a delete older than that can be missing although nobody brought the record back: such a delete is HELD on the phone that has it (`_tombsHeld`, `reconcileTombs`) and deletes nothing by itself (round 3, re-review 1 and 4): it is never published or queued from the phone; it goes back to the log only when this session has read that list FROM THE CLOUD (never the phone's copy, never a read that failed; visits: every month read) and found the record absent (`settleHeldTombs` in `loadAllNow` → `publishConfirmedTombs`) — at that refresh, not at the phone's next delete — and only once the hold has stood `HELD_SETTLE_MS` (5 minutes, counted across reopenings: `um_tombsHeldAt`). - Visit photos with no signal (v122): a visit is saved first and never waits for an upload. Which rep an ERP line counts for: `UMCore.erpRowRep` only — a sale to a known clinic counts for its owner (a handover keeps earlier lines with `prevRep` before `repSince`); a clinic marked `shared` (hospitals, MOH, universities; toggled in Admin → Territory) counts each invoice for the salesman who issued it from `sharedSince` (v97). Owner's confirmation (v100): sales count for the clinic owner whoever invoiced, except shared accounts; every invoice a team member issued at another rep's clinic this month is listed on the Today target card (`UMCore.crossInvoices`). Ownership changes in bulk: Admin → Territory → "Upload a clinic distribution" (or drop the file on the ERP import) — `UMCore.parseDistribution` / `planDistribution` show every change first and save only on tap; names are matched exactly or as a branch family, never guessed (v98).
