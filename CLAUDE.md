# UltraMed Field Ops — working notes for Claude

Kuwait dental-products field-sales PWA (two reps + a supervisor). Everything the
team sees must be true: never report "saved" when it did not land, never show a
figure that cannot be explained on screen.

## Layout
- `www/index.html` — markup and CSS only. The app script is split by area into `www/js/app/01-config.js` … `14-ui-boot.js`, loaded in that order as classic scripts sharing ONE global scope (a function in file 07 may call one in file 12 at run time; only code that runs at load must not reference a later file). Add new code to the file whose area it belongs to (a new file needs its two-line header and a `<script src>` tag in the block, in number order). `APP_REV` (top of `01-config.js`) must match `CACHE` in `www/sw.js`; bump both on every release.
- `scripts/build.js` builds what GitHub Pages publishes (`dist/`, git-ignored): the js/app files are inlined back into ONE `<script>` in index.html, so phones get a single self-contained page exactly as before the split. Never list `js/app` files in the service worker's `SHELL` (the build refuses).
- `www/js/core.js` — pure, unit-tested helpers (dates, ERP parsing, merges, month achievement, the daily e-mail digest). Browser-free; `require`-able from Node.
- `www/js/i18n.js` — the English → Arabic dictionary (exact-string matches).
- Weekly management deck (More → "Weekly management deck", supervisor; v111): `UMCore.weeklyReport` computes the week, `UMCore.weeklyStory` keeps only true achievements and `UMCore.weeklyPages` writes every page's text and figures (all pure, unit-tested); `15-weekly-deck.js` only lays them out with PptxGenJS, loaded on demand from `www/js/vendor/pptxgen.bundle.js` (MIT, vendored — no CDN). Harness: `tests/e2e/weekly-deck.e2e.js`. Order (directors' panel): the week's money on one page (four fixed tiles: the week against last week and the earlier weeks' average, the month against target, new business, the average discount), the closed month on days 1–10, the month's plan (counted to the ERP cut-off: what is left, per working day, the same days of last month, named levers), new business, what sold, price discipline, doctors and clinics, the people (the same rows for everyone), next week, our commitments with "Our ask" (only on the close), then the full appendix (A0 contents … A13 method). Truth rules: an invoice above its discount limit is never a hero, a signature or a cover item; the presenter's own sale never leads the cover; the 8-week page runs only when sales lead; samples are not discount; no score where nothing was measured; brands are net of returns, products as invoiced. Language: English, Arabic or both (two files); the speaker notes are Arabic in both. Arabic uses the team's terms, never a literal translation (مبيعات مفوترة، منتجات تدخل العيادات لأول مرة، حسابات رئيسية، المحقق منذ بداية الشهر …), the team's names in Arabic (مريم، رانوفا، د. غيث), pages, tables and charts mirrored right to left. `wdArBidi` adds the bidi marks LibreOffice and PowerPoint need: RLM after "،" only (never a mark between a letter and "،" or "؛" — it garbles the word), LRM before percentages and digit-led Latin names, a negative written as a word or an operator, an amount kept with its currency by a no-break space; a hyperlink run carries one script only. Design (v110): the Smart Vending look — Calibri, dark green 0B2A1B, Ultramed green 1E7A55, yellow F2B705, light cards EEF4F0; `wdIcon` = the app's own line icons. Company-internal ERP accounts ("Marketing …", "… Advertisement": `UMCore.isInternalAccount`) are never wins, and their zero-value moves are not listed as invoices.
- KPI scorecard (More → "KPI scorecard"; v104): `UMCore.kpiScorecard` scores each person on 10 weighted measures (`KPI_ITEMS`; limits in `BENCHMARKS.kpi`, defaults `KPI_DEFAULTS`, edited in "KPI settings" by the supervisor — `saveBenchmarks` must keep `kpi`). Requests, escalations and stands (More → "Requests, escalations & stands", `16-kpi.js`) are stored in `events` with `kind` and `at` and NO `date`, so the calendar and reports ignore them. Government accounts: `UMCore.isGovClinic` (name pattern, overridden by the Gov chip in Admin → Territory). Plan entries carry `at` (time the clinic was planned) so "plan sent before leaving" can be scored. Harness: `tests/e2e/kpi.e2e.js`.
- Month by month (More → "Month by month", and two slides in the weekly deck; v105): `UMCore.monthlyTrend` — each month's achieved from `monthAchievement` as of its last day, its own DSR target from `UMCore.targetOf` (live target if it belongs to that month, else `targets._history[month]`), day 1–N of every month for a fair comparison with the running month; a month no sales file of that person covers shows "no sales file" (never 0); no KPI for a month with no visit logged.
- Product catalog: the `products` document (seeded once from `PRODUCTS_SEED` for a new account; an existing catalog never re-seeds). `INTENSIV_PRODUCTS` (01-config.js) holds the Intensiv handpieces and Ortho-Strips with their ERP codes as ids — no prices (v121): each is priced from the sales files (the usual invoiced unit price), or left blank. Products → "N products missing from the catalog" (supervisor; `UMCore.catalogGaps`) offers that list plus anything sold in the ERP files under a brand the catalog has none of (services, delivery, packaging, marketing items and kits excluded) and adds only what is ticked; a failed save adds nothing (v106). Products → "Duplicate SKUs / barcodes" (supervisor; `UMCore.productDuplicates`, v121, owner's request): products sharing an item code (`id`) or a barcode (compared as GTINs: digits, leading zeros dropped), listed for review with a copyable report — never merged or deleted. Harness: `tests/e2e/catalog-gaps.e2e.js`.
- ERP account links (v113, supervisor): `erpMap` {ERP customer name: clinicId | '@channel' | '@ignore'} decides which clinic/branch an account's invoices count on. It changes only per account through `saveErpLink` (11-erp.js): a compare-and-set in one storage transaction; memory and the device copy follow the cloud's confirmation only; `persist('erpMap')` is refused and a queued 'erpMap' is dropped from the outbox; a save that lands late never repaints a sheet the person kept working on. Every change goes editor → "Check before saving" (`UMCore.erpLinkPreview`: what moves month by month and per person, checked against `monthAchievement`; a change that touches a closed month needs the explicit tick) → Save → Undo (a branch created in the flow is removed with the Undo when nothing of its own is on it, else the note says why it stays). Entry points: clinic card "ERP accounts counted here" (Move… / Count another account here…, incl. "New branch with this name"), the reconciliation audit (تغيير), the Unrecognized list (Link…), the import screen card → `openErpLinks` (every account, `UMCore.erpAccounts`). `erpMapLog` keeps who changed what (best effort, capped). ERP names reach handlers only through data-* attributes and prototype-safe keys. Harnesses: `tests/e2e/erp-links.e2e.js`, `tests/e2e/erp-links-late.e2e.js`.
- Prescriptions given on a visit (v114): a field visit carries `v.rx = [{type, name, qty, doctorId|null}]` — PADS (the owner counts pads; sheets per pad are unknown, never convert) per prescription type for each person met, or the clinic with no one person (null); step 4 "Prescriptions given?" in the visit form, also in Edit visit. Types: `state/rxTypes` {rev, types:[{id, name, active}]} edited by the supervisor (Doctors → Prescriptions → Prescription types) and saved only by compare-and-set on `rev` (`saveRxTypes`; `persist('rxTypes')` is refused); until he saves, the owner's two printed forms are the built-in list (`UMCore.RX_DEFAULT_TYPES`: "Ultramed fast moving products", "Tepe prescription"). Type names are data, never translated; `_rxTypesRead` keeps "never read" apart from "not set up yet". One path: `UMCore.visitRxLines` (read), `cleanVisitRx` (save), `rxLedger` → `rxGrowth` / `doctorAnalytics` for every figure (Doctors tab, profile, badge, exports, visits CSV); old doctor-profile 'prescription' handovers count once and the profile no longer offers that kind; same-days comparisons, growth from zero says "from zero". `persist()` reports each call's own outcome (`persistFor`), so visit toasts are always the real result. Harness: `tests/e2e/visit-rx.e2e.js`.
- Clinics screen ERP card = the month figure (v115): the month's lines come from ONE pass, `UMCore.erpMonthLines` (files overlapping the month whose rows loaded, returns policy applied, lines dated in the month, credited by `erpRowRep`'s rule), shared by `erpMtd` and `UMCore.monthCustomerSales` (who bought, per person split clinics + online / channels + ignored accounts, `centsSplit` so the parts as shown add up to the total as shown). The dashboard's top tile is "Orders logged in visits · all time" (app-logged orders, never called sales). A claim ("the Today screen figure", "as in the Months report") is made only for people that screen lists (REPS for a supervisor, herself for a rep); someone the files still credit but off the team list is named as such. The DSR upload sheet shows the targets and brand split only, never the DSR's own achieved. Owner's confirmation (11 Oct, v115): sales keep counting for the clinic owner (not the ERP salesman), so a rep's figure can differ from the ERP table filtered by her name by the invoices listed under "Invoices on another rep's clinic". Harness: `tests/e2e/clinics-vs-today.e2e.js`.

One counter covers every list: `persist` and `persistVisits` move it before and after each save, and a refresh that read while a save ran keeps the lists in memory; a flow that changes memory and then waits before or between its writes runs inside `holdRefresh(fn)` (restores, the Admin missing-clinics bring-back). The offline queue lives in memory as well as on the phone (a full phone never loses a queued visit; a queued key whose device copy could not be written is served from memory, with a red bar until it uploads). - Visit photos with no signal (v122): a visit is saved first and never waits for an upload. Each photo is `{id, thumb, pending: true, dev, at}` on the visit (`photoMark`, 12-reports.js; `dev` = this phone's `um_device`, `at` = when it was taken) — the thumbnail inline, the full photo kept on the phone that took it (`_photoKept`: IndexedDB `um_photos`, else web storage `um_photo:<id>`, else memory only, said) and uploaded in the background to `photo:<id>`; the queue's flush (every 20-second refresh) retries. A mark only moves forward, waiting → lost → uploaded (`UMCore.settlePhotoMark` / `settlePhotoMarks`, also in `mergeById`): when a photo lands the phone drops its copy and `settlePhotos` clears THAT mark only, in the document holding the visit (`patchVisitPhotos`, 04-sync.js — a transaction in the visits save chain; a month's archive also moves its index revision, retried until it lands (`_visitsIdxOwed` — owed when any run of the transaction asked to write, its answer lost or late too, and never held back by a look-up that finds nothing), and the phone NEVER takes that revision as its own: its copy of the month is not what the cloud holds, so its next refresh reads the month again — taken, it stopped reading the month and its next save put its old copy back, even dropping a visit moved between two past months) — never a whole-list save, which wrote the phone's older copy of every visit over other phones' edits. The phone also settles its own marks it still owes on every round: a landing whose save did not land, "waiting" put back by an older app version, and its own waiting photo it no longer holds — looked up once in the cloud: there → uploaded; not there → the phone's stores are read again for it (another tab of the app may keep it: then it is sent from here); in neither, and no other tab of the phone holds it (asked over `BroadcastChannel('um_photos')`, 1 s) → lost (the visit keeps the small preview and says so; a verdict whose save fails is sent again, `_photoLost`). The cloud look-up runs even while the phone's stores are not read (a hit settles the mark; a miss gives no verdict until they are read). An IndexedDB that opened on this phone before (`um_idbOk`) but does not open now, or does not answer within 5 s (`photoDb` → false), is "not read" — never "nothing kept" — and no photo of that phone is called lost meanwhile; only a phone with no IndexedDB, or where it never opened, has nothing kept there. A photo the phone let go of this session (landed, removed) is never read back from a store whose delete lags (`_photoGone`). A photo whose phone was reset never settles: after 3 days every OTHER phone says its age and that it can only come from the phone that took it, if that phone still has it (`PHOTO_STALE_DAYS`); the phone whose mark it carries never says that, says at once what it knows (landed → not waiting, `_photoLost` → lost), and reads its stores at start whatever the signal (`photoReadKeptQuiet`, from flushOutbox). `persistVisitsInner` records what it stored as the exact string each transaction committed (`writtenStr`), never the screen's objects, so an edit made while a save commits is saved by its own save. Log visit: the double-tap guard belongs to the form (`_logFormGen`, bumped by `prepLogView`): the form being saved is locked and says "Saving the visit…", a new form saves at once, and the end of a save moves to Today only from that same form. Every screen says only what is true: the note under a visit's thumbnails counts per photo (kept on this phone / only in the app's memory / lost), the gallery marks waiting (⏳) and lost (⚠️) photos, the lightbox shows the full photo from the phone or the cloud, else the visit's thumbnail enlarged with what it is (never an empty frame), the red bar stays while a photo is only in memory, "Offline changes uploaded & merged" names the photos still on their way and is said only when the queue is empty, and the full backup carries the photos still kept on the phone — those held when it began and any this phone saw land during the read are read again among the cloud's documents; one that cannot be read again is listed apart as "reached the cloud while the backup was being read", never as a change the cloud lacks; a photo store that did not answer is said on the screen. Removing a photo kept only in memory never says "Saved — it reached the cloud" (`_memPhotoLanded`: only a landing does, and a landing while more is left on the bar is said at once: "A photo reached the cloud"). Team chat and memories (same release): loadTeam keeps a list that has a save on its way or a queued change (`_teamGen` / `_teamSaving`, per list, the v121 rule; the lists only grow, so a union loses nothing); a save never puts back the copy it took; a share is guarded per memory and clears only its own sheet; the toasts say the real outcome; "Refresh messages" says "Up to date" only after a real read of every list on screen with nothing of this phone's for it saving or queued (a list read while its save ran is read again once that save is over, 5 s at most, and the word is chosen when it is said — a list whose queued change uploaded or whose save landed meanwhile is read once more, each list at most once; `loadTeam` says what each read did — 'cloud' / 'queued' / 'kept' / 'phone' — from `cloudGet`'s `src`, the session-wide read flags cleared before each read); `teamMerge` keeps one entry per id from both lists, every read too (v121 could store a memory three times under one id). Harnesses: `tests/e2e/visit-photo-offline.e2e.js`, `tests/e2e/visit-photo-sync.e2e.js`, `tests/e2e/photo-lifecycle.e2e.js` (past months, tabs, a failing or silent IndexedDB, retried verdicts, age, backup), `tests/e2e/photo-honesty.e2e.js`, `tests/e2e/team-chat.e2e.js`.

## Tests (run before every push)
- `npm test` — unit tests in `tests/*.test.js` (core helpers, daily report).
- `npm run e2e` — browser harnesses on the source; `npm run e2e:dist` — the same on the built site. Harnesses live in `tests/e2e/*.e2e.js` (Playwright + Chromium, a fake cloud, a fixed clock). Run one with `node tests/e2e/smoke-all.e2e.js`. `WWW=<path>` points them at another checkout; `CHROME_PATH` picks a browser (the Claude cloud container's is found automatically).
- GitHub Actions runs both on every push (`.github/workflows/tests.yml`).
- Harness numbers use a synthetic ERP file generated by `tests/e2e/fixtures/make-sales-xlsx.js` — do not commit real sales files.

## House rules
- Arabic replies to the user, plain language, no code in prose.
- Reproduce a bug with a harness check before fixing it; keep the check.
- Team: `REPS` = every `rep` plus every supervisor who sells — a supervisor sells unless `sells: false` (Admin → Team → "Also sells" off), and then owns clinics, a target, a scorecard, a personal daily e-mail and every rep screen exactly like a rep (`tests/e2e/seller-parity.e2e.js` checks each one against Mariam). He can always log a visit under his own name. A clinic handed over carries `prevRep` + `repSince` (1st of the month of the handover): ERP lines dated before `repSince` stay with `prevRep` (`UMCore.clinicRepOn`), so closed months never move.
- Month figures: one code path (`UMCore.monthAchievement`) serves the Today card, the reports, the monthly close and the e-mail — never compute them elsewhere. Rule (owner's decision, v92): the ERP sales files are the ONLY measure of achieved — per rep, per brand, for the team, day by day. The DSR supplies the targets only (per brand, per rep total, team total); its achieved columns are stored but never used. No sales file for the month → achieved shows 0 with "no ERP sales file for this month yet". Which rep an ERP line counts for: `UMCore.erpRowRep` only — a sale to a known clinic counts for its owner (a handover keeps earlier lines with `prevRep` before `repSince`); a clinic marked `shared` (hospitals, MOH, universities; toggled in Admin → Territory) counts each invoice for the salesman who issued it from `sharedSince` (v97). Owner's confirmation (v100): sales count for the clinic owner whoever invoiced, except shared accounts; every invoice a team member issued at another rep's clinic this month is listed on the Today target card (`UMCore.crossInvoices`). Ownership changes in bulk: Admin → Territory → "Upload a clinic distribution" (or drop the file on the ERP import) — `UMCore.parseDistribution` / `planDistribution` show every change first and save only on tap; names are matched exactly or as a branch family, never guessed (v98).
