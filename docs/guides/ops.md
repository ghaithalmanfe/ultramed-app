# دليل التشغيل: النسخ والنشر والتراجع

للمالك. ما بين «» نص الشاشة، وما بخط الكود يُكتب كما هو.

## ١. النسخة الليلية المشفّرة
الخطوات كاملة بالعربي في [docs/backup.md ← «خطوات المالك»](../backup.md#خطوات-المالك). باختصار:
1. اصنع العبارة من [صفحة عبارة المرور](https://ghaithalmanfe.github.io/ultramed-app/backup-passphrase.html) ← «اصنع عبارة مرور»، واحفظها في مدير كلمات المرور وعلى ورقة. لا تُقبل عبارة غيرها، وإن ضاعت فلن يفتح أحد النسخ.
2. GitHub ← Settings ← Secrets and variables ← Actions ← New repository secret: `BACKUP_PASSPHRASE` (لازم)، و`BACKUP_LOGIN_EMAIL` مع `BACKUP_LOGIN_PASSWORD` لحساب خاص بالنسخ على بريد الشركة (بدونهما يستعمل حساب الإيميل اليومي). لا حساب المشرف أبدًا.
3. أول نسخة بيدك: Actions ← «Database backup» ← Run workflow ← daily.
4. النجاح: علامة خضراء و«Database backup: done (daily)» وملف تحت Artifacts؛ الملف هو الدليل لا العلامة. «Backup not configured» بلا ملف = سرّ ناقص، والأحمر يذكر السبب في سطر الخطأ الأول.
5. مرة واحدة يفتح مطوّر أول ملف بـ `scripts/backup/nightly/verify.js` حتى «The backup is sound.»، ثم نظرة كل أسبوع على Actions.

تعمل كل ليلة 02:15 والجمعة 02:45 وأول الشهر 03:15 بتوقيت الكويت، وتبقى 14 و60 و90 يومًا.

## ٢. الإيميل اليومي
الأسرار في المكان نفسه: `REPORT_LOGIN_EMAIL` و`REPORT_LOGIN_PASSWORD` (حساب مخصص للمهمة على بريد الشركة)، و`RESEND_API_KEY`، و`MAIL_FROM` (نطاقه موثّق في Resend). واختياريًا في Variables: `MAIL_ALL_DAYS` = 1 للجمعة والسبت، و`MAIL_TO_OVERRIDE` للتجربة. جرّب: «لوحة الإدارة» ← «📧 تقارير الإيميل» ← «▶️ أرسل الآن من GitHub». التفاصيل في [README](../../README.md#daily-e-mail-reports-v87).

## ٣. قواعد الحماية
لا تُنشر مع التطبيق: كلما تغيّر `firestore.rules` الصقه بيدك.
1. Firebase console ← Firestore Database ← Rules ← الصق `firestore.rules` من main.
2. في الكونسول فقط (المستودع عام) وبحروف صغيرة: بريد المشرف مكان `SUPERVISOR_EMAIL…`، وحسابا الإيميل والنسخ مكان `JOB_LOGIN_EMAIL…`. بلا الأول يُرفض ما لا يحفظه إلا المشرف (التارغت والإعدادات وملفات المبيعات)، وبلا الثاني تخرج الإيميلات ولا يُسجَّل إرسالها.
3. Publish. ومرة واحدة في Authentication: أطفئ إنشاء الحسابات (sign-up) وAnonymous.
4. `MIN_APP_REV()` تبقى 0، ولا تُرفع إلا بعد أن تفتح كل الأجهزة الإصدار الجديد.

## ٤. نشر إصدار
1. لا شيء يُنشر بلا موافقتك: ما يُدمج في main يُنشر وحده، فلا دمج في main قبل موافقتك.
2. بعد الدمج: «Tests» أخضر (اختبارات الوحدة والمتصفح)، ثم «Deploy to GitHub Pages» ينشر ذلك الـcommit نفسه. «Tests» أحمر = لا نشر.
3. تحقّق: افتح https://ghaithalmanfe.github.io/ultramed-app/sw.js وفي سطره الأول `ultramed-field-ops-v…` بالرقم الجديد.
4. الكل يفتح التطبيق **مرتين** على كل جهاز: يفتحه، ينتظر قليلًا، يغلقه تمامًا، ثم يفتحه. بعدها «المساعدة والدعم» ← «إصدار التطبيق» = الرقم الجديد.
5. تغيّر `firestore.rules`؟ القسم ٣.

## ٥. التراجع
1. بموافقتك فقط: commit عكسي لدمج الإصدار (`Deploy v…`) على main ثم push عادي، بلا force-push وبلا إعادة كتابة للتاريخ: `git revert -m 1 <الدمج>` ثم `git push origin main`.
2. «Tests» ثم «Deploy to GitHub Pages» ينشران الإصدار السابق، ويعود رقم sw.js.
3. الكل يفتح التطبيق مرتين.
4. رفعتَ `MIN_APP_REV()`؟ أنزِلها أولًا إلى رقم الإصدار السابق أو أقل، وإلا رفضت السحابة حفظه.
5. التراجع يعيد الكود فقط، والبيانات في السحابة تبقى كما هي. والإصدار التالي برقم جديد.

## ٦. ممنوع مع بيانات الإنتاج
- أي تغيير بلا نسخة احتياطية مستقلة وموافقتك، ولا دمج تلقائي للسجلات.
- الاسترجاع فوق الإنتاج إلا كما في [docs/backup.md ← «Restore into production (last resort)»](../backup.md#restore-into-production-last-resort).
- تعديل مستندات `state` أو حذفها بيدك من الكونسول.
- بيانات حقيقية، أو ملف مبيعات، أو ملف نسخة (`.umbackup` أو المفكوك منه) في المستودع العام.
- بريد أو سرّ داخل `firestore.rules` في المستودع أو في سجل Actions.
- حساب المشرف لمهمة آلية.
